## 0. 本書の位置づけ

当初の構想は「画像から、アイビスペイントのように線画・パーツごとにレイヤーを分け、レイヤーごとの編集を可能にするアプリ」である。
本書ではこの構想を以下の観点でブラッシュアップし、実装着手可能な粒度の仕様に落とし込む。

1. **何が本質的な価値か**を明確にする（→ 1章）
2. **入力画像の種類によって技術難度が大きく異なる**ことを整理し、段階的に対応範囲を広げる（→ 3章）
3. **自動分解の処理パイプライン**を具体化する（→ 5章）
4. **既存ペイントアプリと同等のレイヤー編集機能**のうち、MVP に必要な範囲を定める（→ 6章）
5. 未決事項・リスクを明示する（→ 11章・12章）

> 注: 「アイビスペイント」は操作感・機能水準の参考として挙げているのみで、UI デザイン・名称・アイコン等の模倣は行わない。本アプリは独自の UI として設計する。

## 1. コンセプト

### 1.1 一文で

**「1枚の画像を読み込むだけで、線画レイヤーと塗りパーツのレイヤーに自動で分解し、そのまま描き足し・塗り直しができるペイントアプリ」**

### 1.2 解決する課題

| 課題 | 現状のやり方 | 本アプリでの解決 |
|---|---|---|
| 紙に描いた線画をデジタルで塗りたい | スキャン → 白を透過する線画抽出 → 手作業で塗り分け | 線画抽出と塗り分け領域の生成を自動化 |
| 1枚絵（統合済み画像）の一部だけ色を変えたい | 選択範囲を手で作り、色調補正 | パーツ単位のレイヤーに分かれるため、レイヤー単位で色替え可能 |
| 下塗り（パーツごとのベタ塗り）が面倒 | 閉領域ごとにバケツ塗り、隙間を手で埋める | 閉領域検出＋隙間閉じで下塗りレイヤーを自動生成 |

### 1.3 主なターゲットユーザー

- 紙で線画を描き、デジタルで彩色する趣味〜セミプロのイラスト描き
- 既存の自作イラスト（レイヤー情報を失った統合画像）を再編集したい人
- 塗り絵・配色検討をしたい人（線画に対して配色パターンを試す）

### 1.4 スコープ外（明示）

- 他者の著作物を無断で分解・改変することを目的とした機能（利用規約で自作画像または権利を有する画像の利用に限定する）
- 写真の高度なレタッチ（本アプリはイラスト・線画を主対象とする）
- アニメーション機能

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| 線画レイヤー | 輪郭線のみを保持し、線以外を透明にしたレイヤー。線の濃淡はアルファ値で表現する |
| パーツ | 線画で囲まれた閉領域、または同一色・同一意味（髪・肌・服など）でまとめられた領域 |
| パーツレイヤー | 1パーツの塗りを保持するレイヤー。線画の下に配置する |
| 下塗り | パーツごとのベタ塗り（単色塗り）。陰影は含まない |
| 自動分解 | 入力画像から線画レイヤー・パーツレイヤー群を生成する処理全体 |
| 線下補完 | 線画に隠れていた部分（線の下）をパーツの色で埋め、パーツ境界に隙間が出ないようにする処理 |
| クリッピング | 下のレイヤーの不透明部分にのみ描画を反映させる機能 |
| 透明度保護 | レイヤーの既存の不透明部分にのみ描画を許可する機能（アルファロック） |
| 参照レイヤー | 塗りつぶし（バケツ）・自動選択の判定に、自レイヤーではなく指定レイヤー（主に線画）を使う設定 |

## 3. 入力画像の分類と対応方針

入力の種類によって「線画とパーツの分離」の難しさが本質的に異なる。ここを区別せずに仕様化すると、品質要求が曖昧になるため、以下のように分類する。

| 区分 | 入力例 | 線画抽出 | パーツ分割 | 難度 | 対応フェーズ |
|---|---|---|---|---|---|
| A | 白い紙に黒線のスキャン/撮影、デジタル線画の PNG | 輝度→アルファ変換で高精度に可能 | 線で囲まれた閉領域の検出で可能 | 低 | **MVP** |
| B | 線画＋ベタ塗り（アニメ塗りの下塗り段階、塗り絵完成品） | 線色（暗色）の判定で概ね可能 | 色クラスタリング＋閉領域で可能 | 中 | **MVP** |
| C | 陰影・グラデーション付きの完成イラスト | 色と線の区別が曖昧。機械学習モデルが必要 | 意味的分割（髪/肌/服）は機械学習が必要 | 高 | Phase 2 以降 |
| D | 写真・線のない厚塗り | 「線画」という概念自体が成立しにくい | 意味的分割のみ | 高 | 対象外（将来検討） |

**方針**: MVP は区分 A・B を確実に処理できることを目標とし、区分 C は「線画抽出のみ ML で補助、パーツ分割はユーザー補正前提」で段階的に対応する。

### 3.1 対応ファイル形式（確定）

| 形式 | 判定方法 | 読み込み方法 | 備考 |
|---|---|---|---|
| PNG | 先頭 8 バイトのシグネチャ `89 50 4E 47 0D 0A 1A 0A` | ブラウザの画像デコーダで RGBA に展開 | 透過 PNG は白背景に合成したものとして線画抽出する |
| JPEG | 先頭 3 バイト `FF D8 FF` | 同上 | EXIF の回転情報はブラウザ既定（CSS `image-orientation: from-image`）で適用される |
| SVG | テキストとして解析し、XML 宣言・コメント・DOCTYPE を除いた最初の要素が `<svg` | 指定解像度でラスタライズしてから処理 | 下記参照 |

- 形式の判定は**拡張子や MIME タイプではなく、ファイル先頭のバイト列**で行う（拡張子の付け間違いに強く、偽装ファイルを弾ける）
- 対応外の形式（GIF、WebP、HEIC、gzip 圧縮 SVG `.svgz` など）は理由を示して拒否する。読み込み失敗時は編集中のドキュメントを破棄しない
- ラスタ画像の長辺が上限（4096px）を超える場合は縮小し、その旨を通知する

**SVG の扱い**

- SVG はベクター形式のため解像度を持たない。既定では**長辺 2048px**（上限 4096px）でラスタライズし、以降はラスタ画像と同じパイプラインで処理する
- 論理サイズはルート要素の `width` / `height` / `viewBox` から決める。単位は CSS 絶対単位（1in = 96px, 1cm = 96/2.54px, 1mm, 1pt = 1/72in, 1pc = 12pt, 1Q = 1/4mm）で換算する。`%`・`em` など解決できない単位は `viewBox` にフォールバックし、どちらも無い場合は 300×150 とみなして通知する
- `viewBox` が無い SVG は、論理サイズで `viewBox` を補ってから `width` / `height` を書き換える（`viewBox` 無しで寸法だけ変えると、拡大ではなく切り抜きになるため）
- 安全性: SVG は `<img>` 要素として描画する。この方法ではブラウザが SVG 内のスクリプト実行と外部リソースの読み込みを行わない
- 将来検討: SVG のパス構造を利用した「ベクターのままのパーツ分解」（`<path>` や `<g>` 単位でレイヤー化）。ラスタ処理より高精度になり得るが、SVG の構造は作成ツールによって大きく異なるため Phase 2 以降で評価する

## 4. ユースケース（主要フロー）

### UC-1: 紙の線画を取り込んで塗る（区分 A）

1. ユーザーがカメラ撮影またはファイル（PNG / JPEG / SVG）から画像を読み込む
2. （任意）トリミング・台形補正・回転
3. 自動分解を実行 → 「線画」レイヤーと、閉領域ごとの「パーツ」レイヤー（初期色はパレット自動割当 or 白）が生成される
4. プレビュー画面で、閾値・隙間閉じの強さをスライダーで調整し、結果をリアルタイム確認
5. 確定 → 編集画面へ。パーツレイヤーを選んで色を変える、クリッピングレイヤーを追加して影を描く等

### UC-2: ベタ塗り画像の色替え（区分 B）

1. 画像を読み込み、自動分解を実行
2. 色クラスタごとのパーツレイヤーが生成される（例: 「髪」「肌」「服」…は名前未定のため「パーツ 1, 2, …」として生成し、ユーザーがリネーム）
3. パーツレイヤーの色相・彩度・明度を変更、または単色で塗り替える

### UC-3: 分解結果の手動補正

1. 自動分解の結果、2つのパーツが1つに結合されていた / 1つのパーツが分割されすぎていた
2. 「分割ツール」で線を引いてパーツを分割、「結合」で複数パーツレイヤーを1つに統合
3. 「パーツ移動ブラシ」で領域をなぞり、その画素を別パーツへ移す

### UC-4: 書き出し

1. PNG（統合）、PSD（レイヤー保持）、独自形式（再編集用）で保存
2. 他アプリ（PSD 対応のペイントアプリ）でレイヤー構造を保ったまま開ける

## 5. 自動分解パイプライン（中核機能）

### 5.1 全体像

```
入力画像
  │
  ├─[前処理] 向き補正(EXIF) / リサイズ上限適用 / 色空間を sRGB に正規化
  │
  ├─[1. 線画抽出] ──────────────→ 線画レイヤー（RGBA, 線の濃淡=アルファ）
  │
  ├─[2. 領域分割]
  │     ├ 線画の二値マスク生成
  │     ├ 隙間閉じ（ギャップクロージング）
  │     ├ 閉領域ラベリング
  │     └（区分B）色クラスタリングと統合
  │
  ├─[3. パーツ統合・ノイズ除去] 微小領域を隣接パーツへ吸収
  │
  ├─[4. 線下補完] 線画の下の画素を隣接パーツに割り当て
  │
  └─[5. レイヤー生成] パーツごとにレイヤー化、名前・色・並び順を付与
```

### 5.2 線画抽出

| 方式 | 内容 | 対象 | 備考 |
|---|---|---|---|
| L-1 輝度変換 | `alpha = 1 - 輝度`（輝度は sRGB → リニア変換後ではなく、知覚的明度 L* を推奨）。黒レベル/白レベルの2点補正でコントラスト調整。線色は黒固定または元画像の色を保持（選択可） | 区分 A | アンチエイリアスを保持できる。二値化しないことが重要 |
| L-2 適応的閾値 | 撮影画像の照明ムラ対策として、局所平均との差で背景（紙）を推定してから L-1 を適用 | 区分 A（撮影） | v0.3: L-3 の実装（クロージングによる局所背景推定）で兼ねる |
| L-3 線色判定 | 塗り色と線色を区別：低明度かつ細い構造（線幅推定）を線とみなす | 区分 B | 黒以外の色トレス線は誤判定しやすい → ユーザー補正前提。v0.3 で実装・既定化（5.8） |
| L-4 ML 線画抽出 | 学習済みモデルでイラストから線画を推定 | 区分 C | モデルとライセンスは未選定（11章） |

ユーザー調整パラメータ: 黒レベル、白レベル、線色（黒/元の色/任意色）、ノイズ除去強度。

### 5.3 領域分割

1. **二値マスク**: 線画アルファが閾値 `t`（初期値 0.5、調整可）以上を「線」とする
2. **隙間閉じ**: 線の途切れによって隣接領域がつながるのを防ぐ。候補手法:
   - モルフォロジー膨張（単純だが細部が潰れる）
   - 端点検出＋近傍端点同士の線分接続（線の途切れに特化）
   - Trapped-ball 方式（半径 r のボールが通れない隙間を閉じたものとみなす。Zhang et al., 2009 の手法として知られる）
   → MVP は「膨張 + 端点接続」で実装し、Trapped-ball は比較評価の上で採用判断する
3. **ラベリング**: 線以外の画素について連結成分ラベリング（4近傍）を行う。最外周に接する領域は「背景」として扱う
4. **（区分 B）色クラスタリング**: 元画像の線以外の画素を CIELAB 空間で k-means（k は自動推定 or ユーザー指定）。閉領域ラベルと色クラスタの両方を使い、「同一閉領域内で色が明確に異なれば分割」「異なる閉領域でも同色なら同一パーツにまとめるオプション」を提供

### 5.4 パーツ統合・ノイズ除去

- 面積が `min_area`（初期値: 画像総画素数の 0.01%、調整可）未満の領域は、境界を最も多く共有する隣接パーツに吸収する
- パーツ数の上限（初期値 64）を超える場合は面積の小さい順に吸収する。上限は端末メモリから算出（9章）

### 5.5 線下補完

- 線画の下に隠れていた画素を、**最も近いパーツ**（距離変換によるボロノイ割当）で埋める
- 目的: パーツの色を変えても線の下に白い隙間・元の色の縁が残らないようにする（デジタル塗りでいう「線の下まで塗る」状態を自動で作る）
- パーツレイヤーは線画レイヤーの下に配置されるため、補完部分は表示上は線に隠れる

### 5.6 レイヤー生成

- 生成順（上から）: `線画` → `パーツ 1..N`（面積の大きい順）→ `背景`
- 各パーツレイヤーの初期色:
  - 区分 A: 白、またはユーザー選択の「自動配色」（隣接パーツで色相が離れるよう割当）
  - 区分 B: 元画像のクラスタ代表色
- 各パーツは「1色ベタのレイヤー」として生成するか、「元画像の画素をそのまま切り出したレイヤー」として生成するかを選択可能（区分 B/C では後者が見た目を保持できる）
- 自動分解の結果はまとめて1つのレイヤーフォルダ「自動分解」に入れる

### 5.7 処理性能目標

| 画像サイズ | 目標処理時間（中位スマホ相当, 区分 A） |
|---|---|
| 2048 × 2048 | 3 秒以内 |
| 4096 × 4096 | 10 秒以内 |

- 重い処理は Web Worker 上で実行し、UI をブロックしない。進捗表示とキャンセルを必須とする
- パラメータ調整プレビューは縮小画像（長辺 1024px）で行い、確定時にフル解像度で再計算する

> 注: 上記目標値は実測前の暫定値。PoC（12章 Phase 0）で計測し確定する。v0.3 時点の計測は 5.8 節。

### 5.8 Phase 0 実装結果（v0.3）

5.2〜5.6 の方針のうち、実際に採用した手法と、方針から変えた点を記す。

**線画抽出（L-3 を既定に）**

- 「線らしさ」= (クロージング(L\*) − L\*) / クロージング(L\*) を黒レベル/白レベルで正規化してアルファにする（ブラックトップハットを局所背景の明度で割った相対値）
  - クロージング（一辺 2r+1 の正方形, r = ⌈最大線幅/2⌉）は、それより細い暗い構造を周囲の明るさで埋める。差を取ると「周囲より暗く細い構造」だけが残り、太い塗り（色面・黒ベタ）は線にならない
  - 背景の明度で割るのは、反射率に照明が掛け算で効くため（赤い塗りの上の黒線も完全な線になる）。L\* は非線形なのでこの比は近似
  - 白い紙の上では L-1 と同一の結果になる（テストで確認）。照明ムラのある紙では局所的な紙の明るさが基準になるため L-2 を兼ねる
- 方針からの変更理由: L-1 では明度 L\* が約 63 未満の塗り（例: 赤 L\*≈46）がすべて線と判定され、区分 B の画像でパーツが消えたため
- 既知の限界: 最大線幅（既定 16px）より太い黒ベタは線画ではなくパーツになる。色トレス線は塗りとの明度差が小さいと薄く抽出される

**領域分割（5.3〜5.5）**

| 手順 | 採用した手法 | 方針との差 |
|---|---|---|
| 隙間閉じ | 線マスクの厳密ユークリッド距離変換で、線から gapRadius より遠い画素だけをシードにする（線を半径 gapRadius で膨張させるのと等価。幅 2·gapRadius 以下の途切れを閉じる） | 端点接続は未実装（下記「残課題」） |
| シード | 上記に加え、線画アルファ 0.15 未満の「線の影響を受けていない」画素に限る | 追加。アンチエイリアスの縁が灰色の細いパーツになるのを防ぐ |
| ラベリング | 4 近傍。隣接画素の色差（sRGB ユークリッド距離）が colorTolerance（既定 40）を超える場合はつながない | 5.3-4 の k-means の代わり。線の無い色境界で領域を分ける |
| 線下補完 | シードからの多始点幅優先探索で全画素を最寄り（測地距離）の領域に割り当てる。まず線以外の画素、次に線の下の 2 段階 | 5.5 の「距離変換によるボロノイ割当」の代わり。1 段階だと、シードの無い細い部分に線の向こう側の領域が侵入する |
| 断片の統合 | 色が近く、線上でない境界を共有し、両方とも平均幅（2·面積/境界長）≤ 4·gapRadius+2 の隣接領域を統合 | 追加。隙間閉じは幅 ≒ 2·gapRadius の細い領域を細切れにするため |
| 背景・微小領域・上限 | 外周に接する領域を背景に統合 → 面積 minArea 未満を最長境界の隣接へ吸収 → パーツ数上限 | 5.4 の通り。順序は線下補完の後（隣接の境界長を正確に測るため） |
| レイヤー化 | 外接矩形サイズの 1 色ベタ。塗り色は auto（全パーツが白なら自動配色、そうでなければ元画像の領域平均色） | 元画素の切り出しモードは未実装 |

**品質の確認（合成画像）**

- 単体テスト: 枠による分割、線下補完（全画素が割当済み・線の中央で左右に分かれる）、隙間閉じ（4px は閉じ、9px は閉じない）、1px 斜め線の非貫通、微小領域吸収、パーツ上限、細い領域の非断片化、アンチエイリアス縁、線の無い色境界の分離、照明ムラ
- ブラウザでの確認（800×800 の顔の線画。主要パーツ 8 個 + 髪と輪郭の間の細い隙間 2 個 = 正解 10 個）:

| 入力 | 結果 |
|---|---|
| 線画のみ（gapRadius 2） | 11 個（正解 10 + 98px の断片 1） |
| 線画のみ（gapRadius 0） | 10 個（正解と一致） |
| 色付き（gapRadius 2） | 9 個（主要 8 個は正しい色。細い隙間は背景・髪と一体化、104px の断片 1） |

> 注: 合成画像による確認であり、実際の手描きスキャン画像での評価（12 章の「テスト画像 20 枚程度」）は未実施。

**処理時間（Node.js, 4 コアのクラウド環境, 合成線画, 64 パーツ）**

| サイズ | 合計 | 線画抽出 | 領域分割 | レイヤー化 |
|---|---|---|---|---|
| 1024² | 0.39 秒 | 0.16 | 0.29 | 0.03 |
| 2048² | 1.31 秒 | 0.61 | 0.73 | 0.05 |
| 4096² | 5.79 秒 | 2.60 | 2.97 | 0.22 |

- 処理は単一スレッドで、コア数は効かない。5.7 の目標（中位スマホで 2048² 3 秒、4096² 10 秒）に対し、スマホの単一コア性能は計測環境より低いため、4096² は目標を超える可能性が高い。実機での計測が必要。超える場合は WebAssembly 化、または 5.7 のとおり縮小画像でのプレビューで対応する
- 計測は `npm run bench` で再現できる

**残課題**

1. 端点接続による隙間閉じ: 細い領域のくびれと本物の線の途切れは、距離だけでは局所的に区別できない（どちらも幅 2·gapRadius 以下の線の無い通路）。区別には線の端点の解析が必要。現状の「断片の統合」は両方が細い場合に限って統合するため、細い領域どうしが本物の線の途切れでつながっている場合は誤って統合される
2. 実画像（手描きスキャン・撮影・JPEG）での品質評価と、パラメータ既定値の調整
3. 実機ブラウザでの処理時間計測
4. パラメータ調整の縮小プレビュー（5.7）。タップ選択・分割・結合は v0.4（6.2.1）、パーツ移動ブラシは v0.6（6.2.2）で実装

### 6.2.1 タップ選択・分割・結合の詳細仕様（v0.4 実装済み）

**タップ選択**

- 「選択」ツールでキャンバスをタップすると、その位置にある最前面の表示中パーツを選択する。パーツは線の下まで塗られている（5.5）ため、線の上をタップしても線のどちらか側のパーツが選ばれる
- 移動量 6 CSS px 以下の操作をタップとみなす
- 追加選択: Shift / Ctrl / Cmd を押しながらタップ、または「複数選択」モード（タッチ操作用）でタップ。選択済みのパーツをもう一度タップすると解除
- 何も無い所のタップで選択解除（複数選択モードでも解除する。タッチ操作では他に解除手段が無いため）。修飾キー付きのクリックでは解除しない。Esc キーでも解除
- レイヤーパネルでも同様（クリックで選択、Shift / Ctrl / Cmd + クリックで追加）。プロパティは最後に選んだレイヤーについて表示する
- 選択中のパーツは、その形をアクセント色の半透明で強調表示する

**分割**

- 「分割」ツールでパーツを横切る線を引く。対象は、選択中のパーツ（複数なら最後に選んだもの）、無ければ線の下の画素を最も多く含む表示中パーツ
- 線は幅 3px（ドキュメント座標）の切断線としてラスタライズする。4 近傍の連結を確実に断つため
- 切断線を除いた画素の連結成分のうち、面積が max(16px, パーツ面積の 0.2%) 以上のものを断片とみなす。断片が 2 つ以上できなければ分割しない（線が端から端まで横切っていない、角をかすめただけ、など）
- 切断線上の画素と小さな欠片は、幅優先探索で最寄りの断片に割り当てる（分割で面積が減らない）
- もともと離れていた島（結合したパーツなど）は、切断線が触れていなければ最大のピースに残す。切断線が触れた島だけが分割される
- 最大のピースが元のレイヤーの名前・属性を引き継ぎ、ほかは「元の名前-2」「-3」…として同じ位置に挿入する。色は元の画素のまま。分割後は新しくできた側のピースを選択し、どこが切り離されたか分かるようにする

**結合**

- パーツを 2 つ以上選択し「結合」を押す
- 重なった画素は前面のパーツを採用する。結合後のパーツは、面積が最大のパーツの名前・属性・塗り色を引き継ぎ、全体をその色に揃える（パーツは 1 色ベタのため）
- 結合後のレイヤーは、選択したうち最も前面にあったレイヤーの位置に置く

**共通**

- 分割・結合・色変更はすべて取り消し/やり直しの対象。ロックされたパーツには適用しない
- 対象はパーツ（`role = "part"`）のみ。線画・背景・元画像レイヤーは対象外

### 6.2.2 パーツ移動ブラシの詳細仕様（v0.6 実装済み）

自動分解の境界の誤り（隣のパーツに食い込んだ・取られた部分）を、なぞって直すためのツール。

**移動先**

- 選択中のパーツ（複数なら最後に選んだもの）。選択が無ければ、なぞり始めた位置の最前面のパーツを移動先にし、選択状態にする
  - つまり「広げたいパーツの内側からなぞり始め、隣のパーツへ塗り込む」と、そのパーツが広がる
- 移動先はツールオプションバーに色見本と名前で表示する
- なぞり始めがパーツの無い場所で選択も無いとき、移動先がロックされているときは、何もせずに理由を表示する

**動作**

- ブラシの範囲（直径 = サイズ、ドキュメント px）にある、他のパーツの画素を移動先へ移す。移した画素は移動先の塗り色にする
- 対象は表示中・ロックされていないパーツのみ。線画・背景・元画像レイヤーには触れない
- 移動先にすでにある画素はそのまま。移動元に触れなかった場合は「移せる画素がありません」と表示し、何も変えない
- 移動先の範囲は移した画素を含むよう広がり、移動元は残った画素の外接矩形に縮む。移動元の画素がすべて無くなったらそのレイヤーを削除する
- 1 回のなぞり（押してから離すまで）が 1 回の取り消し単位。結果は「パーツ 5 から『パーツ 1』へ 2,968 px 移しました」のように通知する

**操作**

- ツール: 移動ブラシ（B）。サイズは 1〜200px（既定 20px）。オプションバーのスライダー、または `[` / `]` で変更（刻み: 10px 未満は 1、50px 未満は 5、それ以上は 10）
- カーソルは画面上の円（直径 = サイズ × 表示倍率）。サイズ・倍率の変更に追従する。白黒の二重線で、明暗どちらの背景でも見える
- なぞっている間は、なぞった範囲を移動先の色で半透明に表示する（重なっても濃くならない）
- 2 本指でピンチを始めると、なぞりは取り消す（他のツールと同じ）

**実装上の注意**

- なぞり跡のラスタライズは、円を max(0.5, 半径/4) px 間隔で打つ。縁の凹凸は約 半径/128 px で、半径 128px まで 1px 未満
- 既知の限界: ブラシの縁はアンチエイリアスしない（パーツは不透明な画素で画像を分け合っており、縁を半透明にすると隣り合う両パーツが半透明になって背景が透けるため）。拡大・回転表示では縁の段差が見える

| ツールオプションバー | 選択中ツールのオプション（選択: 複数選択・結合・選択解除、移動ブラシ: サイズ・移動先）と操作ヒント。狭い画面ではツール名を省き、入りきらなければ横スクロール |

### 7.2 表示操作（拡大・縮小・回転・移動）

| 操作 | タッチ | マウス・トラックパッド | キーボード |
|---|---|---|---|
| 拡大・縮小 | 2 本指ピンチ（指の中点を中心に） | Ctrl/Cmd + ホイール（カーソル位置を中心に）。トラックパッドのピンチも同じ | Ctrl/Cmd + `+` / `-`（段階: 2%〜3200%） |
| 移動 | 2 本指ドラッグ | ホイール（Shift で横）、中ボタンドラッグ、Space + ドラッグ、手のひらツール | — |
| 回転 | 2 本指でひねる | — | — |
| 画面に合わせる / 100% | — | 倍率メニュー | Ctrl/Cmd + 0 / Ctrl/Cmd + 1 |
| 回転のリセット | — | 倍率メニュー、ステータスバーの回転角 | — |
| 取り消し / やり直し | 2 本指タップ / 3 本指タップ | — | Ctrl/Cmd + Z / Ctrl/Cmd + Shift + Z |

仕様の詳細:

- 表示変換は「画面 = 平行移動 + 回転 · 倍率 · ドキュメント」の相似変換。ピンチは開始時の指の中点の下にあった絵が、現在の中点に来るように拡大・回転・移動を同時に計算する（`src/ui/viewport.ts`、単体テストあり）
- 回転はピンチ中に 10° を超えてひねった時点で有効になる（拡大だけのつもりで傾くのを防ぐ）。有効化の時点の表示を起点にし直すため、急に 10° 回ることはない。指を離したとき 0°/90°/180°/270° から ±5° 以内なら吸着する
- 2 本指でピンチを始めると、1 本目の指で始まっていたツール操作（タップ選択・分割の線）は取り消す
- 複数本指タップは、300ms 以内・移動 12px 以下のときだけ取り消し/やり直しとみなす
- 倍率 400% 以上では画素をぼかさずに表示（最近傍補間）。それ未満は滑らかに表示（回転時に縁が荒れないため）
- ドキュメントを開いたときは画面に合わせる。ウィンドウの大きさが変わったときは画面中央の位置を保つ
- 選択の強調・分割線はドキュメント座標で描くが、線幅は倍率で割って画面上で一定の太さに見せる

## 8. データモデル

```ts
type Document = {
  id: string;
  name: string;
  width: number;            // px
  height: number;           // px
  dpi: number;              // 既定 350
  root: LayerGroup;
  createdAt: string;        // ISO 8601
  updatedAt: string;
  source?: SourceImageInfo; // 自動分解の元画像情報（再分解用）
};

type LayerNode = Layer | LayerGroup;

type LayerBase = {
  id: string;
  name: string;
  visible: boolean;
  opacity: number;          // 0..1
  blendMode: BlendMode;
  clipping: boolean;        // true: 下のレイヤーにクリッピング
  locked: boolean;
};

type Layer = LayerBase & {
  kind: "raster";
  role: "normal" | "lineart" | "part" | "background";
  alphaLocked: boolean;
  isReference: boolean;
  bitmapId: string;         // ピクセルデータへの参照（IndexedDB/OPFS 上）
  bounds: { x: number; y: number; w: number; h: number }; // 非透明領域の外接矩形
  part?: { fillColor?: string; sourceLabel?: number };      // role=part の付加情報
};

type LayerGroup = LayerBase & {
  kind: "group";
  expanded: boolean;
  children: LayerNode[];    // 先頭が最前面
};

type SourceImageInfo = {
  bitmapId: string;
  category: "A" | "B" | "C";
  params: DecomposeParams;  // 再分解時の初期値
};
```

- ピクセルデータはレイヤーの外接矩形（`bounds`）分のみ保持し、全面サイズを確保しない（パーツレイヤーは画像の一部しか占めないことが多いため、メモリ削減効果が大きい）
- 独自保存形式（`.ldraw`）: ZIP コンテナに `document.json` と各レイヤーの PNG を格納（OpenRaster `.ora` と同様の構造。`.ora` での入出力も Phase 2 で検討）

## 10. 技術構成案

| レイヤー | 採用候補 | 選定理由 |
|---|---|---|
| アプリ形態 | **Web アプリ（PWA）** | スマホ・タブレット・PC を単一コードで対応。インストール不要で試用障壁が低い。将来ネイティブが必要になれば Capacitor 等で包む |
| 言語 / UI | TypeScript + React（または Svelte） | 型安全、エコシステム |
| 描画・合成 | WebGL2（合成モード・クリッピングをシェーダで実装） | Canvas 2D の `globalCompositeOperation` は主要な合成モードを持つが、クリッピング＋合成モードの組合せやフォルダ単位合成、大量レイヤー時の性能でシェーダ実装の方が制御しやすい。WebGPU は対応状況を見て Phase 2 以降で検討 |
| 画像処理 | Web Worker + WebAssembly（OpenCV.js、または Rust 製の自前処理を wasm 化） | 連結成分ラベリング、距離変換、モルフォロジー、k-means を高速に実行 |
| ML 推論（Phase 2） | ONNX Runtime Web（WebGPU / WASM バックエンド） | 端末内推論。モデルは軽量なものに限定 |
| 保存 | IndexedDB / OPFS（Origin Private File System） | 大容量バイナリの保存 |
| PSD 入出力 | `ag-psd`（JavaScript の PSD 読み書きライブラリ） | ライセンス・対応範囲（合成モード、クリッピング、フォルダ）を採用前に確認 |
| テスト | Vitest（単体）、Playwright（E2E）、分解品質は画像データセットによる回帰テスト | |

### 10.1 フレームワーク構成と実装状況（v0.3 時点）

Vite + React + TypeScript。ディレクトリと責務:

| ディレクトリ | 責務 | DOM 依存 |
|---|---|---|
| `src/core/` | データモデル（8章）、ドキュメント操作（イミュータブル）、取り消し履歴、ビットマップ置き場 | `bitmapStore` のみ |
| `src/io/` | 入力形式判定、PNG/JPEG/SVG のデコード、SVG サイズ解決 | `importImage` のみ |
| `src/decompose/` | 自動分解パイプライン（5章）。Web Worker で実行 | なし |
| `src/render/` | レイヤーツリーの合成（`Compositor` インターフェース） | あり |
| `src/store/` | エディタ状態（React Context + useReducer）、分解結果からのドキュメント生成 | あり |
| `src/ui/` | 画面部品（キャンバス、レイヤーパネル） | あり |

設計上の決定:

- **ドキュメントはイミュータブル、ピクセルは ID 参照**: 取り消し履歴はドキュメントのスナップショットで実装し、ピクセルデータは `BitmapStore` に ID で保持する。これによりスナップショットのコストがツリー構造分だけになる。ピクセル編集時は新しい ID を発行する（コピーオンライト）
- **連続操作の履歴**: スライダー操作中は履歴に積まず、操作終了時に 1 ステップとして確定する
- **合成は差し替え可能**: 現在は Canvas 2D 実装（`Canvas2DCompositor`）。`Compositor` インターフェースを保ったまま WebGL2 実装に置き換える
- **自動分解は DOM 非依存**: Worker・単体テストの両方から同じコードを実行できる。キャンセルは Worker の終了と再生成で行う

実装状況:

| 領域分割・パーツ統合・線下補完・レイヤー化 | 実装済み（5.8）。端点接続は未実装 |

### 10.2 配布（v0.7 実装済み）

- **形態**: インストール可能な PWA（Web App Manifest + Service Worker）。Mac では Safari の「Dock に追加」（macOS Sonoma 14 以降）、Chrome / Edge の「アプリとしてインストール」で Dock に置ける
- **公開先**: GitHub Pages（`https://peyangpiece.github.io/layer-draw/`）。既定ブランチへの push で GitHub Actions がテスト・ビルド・公開する（`.github/workflows/pages.yml`）。初回のみリポジトリ設定で Pages の Source を「GitHub Actions」にする
- **パス**: ビルドは相対パス（`base: "./"`）。サブパスや claude.ai の Artifact でもそのまま動く
- **オフライン**: Service Worker はビルド時に生成する（`build/serviceWorkerPlugin.ts`）。出力の全ファイルを事前キャッシュし、キャッシュ名に内容のハッシュを含める
  - ページはネットワーク優先（オンラインなら常に最新、オフラインならキャッシュ）、ハッシュ付きの資源はキャッシュ優先
  - 各版は自分のキャッシュだけを参照する（`caches.match()` は全キャッシュを作成順に探すため、更新の切り替え中に古い版を返す）
  - 生成した sw.js の構文はビルド時に検査する（壊れていると登録に失敗し、オフライン対応が黙って無効になるため）
  - Service Worker を使えない環境（Artifact など）では登録を諦め、オフライン対応なしで動く
- **ファイルから起動**: マニフェストの `file_handlers` で PNG / JPEG / SVG を受け付け、`launchQueue` で受け取って開く（Chrome / Edge のみ）
- **アイコン**: macOS のアイコン格子に合わせた角丸版（`any`）と、全面を塗った版（`maskable`、`apple-touch-icon`）
- **確認済み（Chromium）**: インストール可能性の検査でエラーなし、Service Worker の制御、オフライン起動とオフラインでの自動分解、更新時のキャッシュ入れ替え
- **未確認**: Safari（WebKit）での動作と「Dock に追加」の見た目。この開発環境に WebKit が無いため、Mac の実機で確認する

## 13. 受け入れ基準（MVP）

1. 白背景・黒線の線画 PNG（2048×2048）を読み込み、自動分解の結果として「線画」レイヤー1枚と、閉領域ごとのパーツレイヤーが生成される
2. 線画レイヤーは線以外が完全透明（アルファ 0）であり、線のアンチエイリアスが保持されている（二値化されていない）
3. 線の途切れ幅が既定パラメータ以下（例: 3px 以下）の場合、途切れの両側が別パーツとして分割される
4. 任意のパーツの色を変更したとき、線と塗りの間に元の背景色（白）の隙間が見えない（線下補完の検証）
5. 自動分解の処理中に UI が操作不能にならず、キャンセルできる
6. 6.1 の全レイヤー操作が動作し、取り消し/やり直しが 50 ステップ以上可能
7. 保存→再読込で、レイヤー構造・合成モード・クリッピング・不透明度が完全に復元される
8. 機内モード（オフライン）で 1〜7 がすべて動作する

## 14. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 線の途切れ・ノイズにより分割品質が安定しない | 体験の中核が損なわれる | プレビューでのパラメータ調整と手動補正ツール（6.2）を MVP に含める。テスト画像セットで回帰評価 |
| モバイルブラウザのメモリ制限 | 大きな画像・多数レイヤーでクラッシュ | 外接矩形保持、パーツ数上限、入力サイズ上限、実機での上限計測 |
| ML モデルのライセンス・学習データ問題 | 商用利用不可、公開後の差し替え | 採用前にライセンス・学習データの出自を確認し記録。区分 A/B は ML 不要で成立させる |
| 既存アプリとの類似 | 権利上の問題 | UI・名称・アイコンは独自設計。機能水準の参考に留める |
| ユーザーが他者の画像を分解・改変 | 著作権侵害の助長 | 利用規約で自作または権利を有する画像に限定する旨を明記 |
