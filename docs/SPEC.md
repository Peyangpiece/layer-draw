## 0. 本書の位置づけ

当初の構想は「画像から、アイビスペイントのように線画・パーツごとにレイヤーを分け、レイヤーごとの編集を可能にするアプリ」である。
本書ではこの構想を以下の観点でブラッシュアップし、実装着手可能な粒度の仕様に落とし込む。

1. **何が本質的な価値か**を明確にする（→ 1章）
2. **入力画像の種類によって技術難度が大きく異なる**ことを整理し、段階的に対応範囲を広げる（→ 3章）
3. **自動分解の処理パイプライン**を具体化する（→ 5章）
4. **既存ペイントアプリと同等のレイヤー編集機能**のうち、MVP に必要な範囲を定める（→ 6章）
5. 未決事項・リスクを明示する（→ 11章・12章）

> 注: 「アイビスペイント」は操作感・機能水準の参考として挙げているのみで、UI デザイン・名称・アイコン等の模倣は行わない。本アプリは独自の UI として設計する。

## 1. コンセプト

### 1.1 一文で

**「1枚の画像を読み込むだけで、線画レイヤーと塗りパーツのレイヤーに自動で分解し、そのまま描き足し・塗り直しができるペイントアプリ」**

### 1.2 解決する課題

| 課題 | 現状のやり方 | 本アプリでの解決 |
|---|---|---|
| 紙に描いた線画をデジタルで塗りたい | スキャン → 白を透過する線画抽出 → 手作業で塗り分け | 線画抽出と塗り分け領域の生成を自動化 |
| 1枚絵（統合済み画像）の一部だけ色を変えたい | 選択範囲を手で作り、色調補正 | パーツ単位のレイヤーに分かれるため、レイヤー単位で色替え可能 |
| 下塗り（パーツごとのベタ塗り）が面倒 | 閉領域ごとにバケツ塗り、隙間を手で埋める | 閉領域検出＋隙間閉じで下塗りレイヤーを自動生成 |

### 1.3 主なターゲットユーザー

- 紙で線画を描き、デジタルで彩色する趣味〜セミプロのイラスト描き
- 既存の自作イラスト（レイヤー情報を失った統合画像）を再編集したい人
- 塗り絵・配色検討をしたい人（線画に対して配色パターンを試す）

### 1.4 スコープ外（明示）

- 他者の著作物を無断で分解・改変することを目的とした機能（利用規約で自作画像または権利を有する画像の利用に限定する）
- 写真の高度なレタッチ（本アプリはイラスト・線画を主対象とする）
- アニメーション機能

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| 線画レイヤー | 輪郭線のみを保持し、線以外を透明にしたレイヤー。線の濃淡はアルファ値で表現する |
| パーツ | 線画で囲まれた閉領域、または同一色・同一意味（髪・肌・服など）でまとめられた領域 |
| パーツレイヤー | 1パーツの塗りを保持するレイヤー。線画の下に配置する |
| 下塗り | パーツごとのベタ塗り（単色塗り）。陰影は含まない |
| 自動分解 | 入力画像から線画レイヤー・パーツレイヤー群を生成する処理全体 |
| 線下補完 | 線画に隠れていた部分（線の下）をパーツの色で埋め、パーツ境界に隙間が出ないようにする処理 |
| クリッピング | 下のレイヤーの不透明部分にのみ描画を反映させる機能 |
| 透明度保護 | レイヤーの既存の不透明部分にのみ描画を許可する機能（アルファロック） |
| 参照レイヤー | 塗りつぶし（バケツ）・自動選択の判定に、自レイヤーではなく指定レイヤー（主に線画）を使う設定 |

## 3. 入力画像の分類と対応方針

入力の種類によって「線画とパーツの分離」の難しさが本質的に異なる。ここを区別せずに仕様化すると、品質要求が曖昧になるため、以下のように分類する。

| 区分 | 入力例 | 線画抽出 | パーツ分割 | 難度 | 対応フェーズ |
|---|---|---|---|---|---|
| A | 白い紙に黒線のスキャン/撮影、デジタル線画の PNG | 輝度→アルファ変換で高精度に可能 | 線で囲まれた閉領域の検出で可能 | 低 | **MVP** |
| B | 線画＋ベタ塗り（アニメ塗りの下塗り段階、塗り絵完成品） | 線色（暗色）の判定で概ね可能 | 色クラスタリング＋閉領域で可能 | 中 | **MVP** |
| C | 陰影・グラデーション付きの完成イラスト | 色と線の区別が曖昧。機械学習モデルが必要 | 意味的分割（髪/肌/服）は機械学習が必要 | 高 | Phase 2 以降 |
| D | 写真・線のない厚塗り | 「線画」という概念自体が成立しにくい | 意味的分割のみ | 高 | 対象外（将来検討） |

**方針**: MVP は区分 A・B を確実に処理できることを目標とし、区分 C は「線画抽出のみ ML で補助、パーツ分割はユーザー補正前提」で段階的に対応する。

### 3.1 対応ファイル形式（確定）

| 形式 | 判定方法 | 読み込み方法 | 備考 |
|---|---|---|---|
| PNG | 先頭 8 バイトのシグネチャ `89 50 4E 47 0D 0A 1A 0A` | ブラウザの画像デコーダで RGBA に展開 | 透過 PNG は白背景に合成したものとして線画抽出する |
| JPEG | 先頭 3 バイト `FF D8 FF` | 同上 | EXIF の回転情報はブラウザ既定（CSS `image-orientation: from-image`）で適用される |
| SVG | テキストとして解析し、XML 宣言・コメント・DOCTYPE を除いた最初の要素が `<svg` | 指定解像度でラスタライズしてから処理 | 下記参照 |

- 形式の判定は**拡張子や MIME タイプではなく、ファイル先頭のバイト列**で行う（拡張子の付け間違いに強く、偽装ファイルを弾ける）
- 対応外の形式（GIF、WebP、HEIC、gzip 圧縮 SVG `.svgz` など）は理由を示して拒否する。読み込み失敗時は編集中のドキュメントを破棄しない
- ラスタ画像の長辺が上限（4096px）を超える場合は縮小し、その旨を通知する

**SVG の扱い**

- SVG はベクター形式のため解像度を持たない。既定では**長辺 2048px**（上限 4096px）でラスタライズし、以降はラスタ画像と同じパイプラインで処理する
- 論理サイズはルート要素の `width` / `height` / `viewBox` から決める。単位は CSS 絶対単位（1in = 96px, 1cm = 96/2.54px, 1mm, 1pt = 1/72in, 1pc = 12pt, 1Q = 1/4mm）で換算する。`%`・`em` など解決できない単位は `viewBox` にフォールバックし、どちらも無い場合は 300×150 とみなして通知する
- `viewBox` が無い SVG は、論理サイズで `viewBox` を補ってから `width` / `height` を書き換える（`viewBox` 無しで寸法だけ変えると、拡大ではなく切り抜きになるため）
- 安全性: SVG は `<img>` 要素として描画する。この方法ではブラウザが SVG 内のスクリプト実行と外部リソースの読み込みを行わない
- 将来検討: SVG のパス構造を利用した「ベクターのままのパーツ分解」（`<path>` や `<g>` 単位でレイヤー化）。ラスタ処理より高精度になり得るが、SVG の構造は作成ツールによって大きく異なるため Phase 2 以降で評価する

## 4. ユースケース（主要フロー）

### UC-1: 紙の線画を取り込んで塗る（区分 A）

1. ユーザーがカメラ撮影またはファイル（PNG / JPEG / SVG）から画像を読み込む
2. （任意）トリミング・台形補正・回転
3. 自動分解を実行 → 「線画」レイヤーと、閉領域ごとの「パーツ」レイヤー（初期色はパレット自動割当 or 白）が生成される
4. プレビュー画面で、閾値・隙間閉じの強さをスライダーで調整し、結果をリアルタイム確認
5. 確定 → 編集画面へ。パーツレイヤーを選んで色を変える、クリッピングレイヤーを追加して影を描く等

### UC-2: ベタ塗り画像の色替え（区分 B）

1. 画像を読み込み、自動分解を実行
2. 色クラスタごとのパーツレイヤーが生成される（例: 「髪」「肌」「服」…は名前未定のため「パーツ 1, 2, …」として生成し、ユーザーがリネーム）
3. パーツレイヤーの色相・彩度・明度を変更、または単色で塗り替える

### UC-3: 分解結果の手動補正

1. 自動分解の結果、2つのパーツが1つに結合されていた / 1つのパーツが分割されすぎていた
2. 「分割ツール」で線を引いてパーツを分割、「結合」で複数パーツレイヤーを1つに統合
3. 「パーツ移動ブラシ」で領域をなぞり、その画素を別パーツへ移す

### UC-4: 書き出し

1. PNG（統合）、PSD（レイヤー保持）、独自形式（再編集用）で保存
2. 他アプリ（PSD 対応のペイントアプリ）でレイヤー構造を保ったまま開ける

## 5. 自動分解パイプライン（中核機能）

### 5.1 全体像

```
入力画像
  │
  ├─[前処理] 向き補正(EXIF) / リサイズ上限適用 / 色空間を sRGB に正規化
  │
  ├─[1. 線画抽出] ──────────────→ 線画レイヤー（RGBA, 線の濃淡=アルファ）
  │
  ├─[2. 領域分割]
  │     ├ 線画の二値マスク生成
  │     ├ 隙間閉じ（ギャップクロージング）
  │     ├ 閉領域ラベリング
  │     └（区分B）色クラスタリングと統合
  │
  ├─[3. パーツ統合・ノイズ除去] 微小領域を隣接パーツへ吸収
  │
  ├─[4. 線下補完] 線画の下の画素を隣接パーツに割り当て
  │
  └─[5. レイヤー生成] パーツごとにレイヤー化、名前・色・並び順を付与
```

### 5.2 線画抽出

| 方式 | 内容 | 対象 | 備考 |
|---|---|---|---|
| L-1 輝度変換 | `alpha = 1 - 輝度`（輝度は sRGB → リニア変換後ではなく、知覚的明度 L* を推奨）。黒レベル/白レベルの2点補正でコントラスト調整。線色は黒固定または元画像の色を保持（選択可） | 区分 A | アンチエイリアスを保持できる。二値化しないことが重要 |
| L-2 適応的閾値 | 撮影画像の照明ムラ対策として、局所平均との差で背景（紙）を推定してから L-1 を適用 | 区分 A（撮影） | 背景推定は大きめのぼかし or モルフォロジー closing で行う |
| L-3 線色判定 | 塗り色と線色を区別：低明度かつ細い構造（線幅推定）を線とみなす | 区分 B | 黒以外の色トレス線は誤判定しやすい → ユーザー補正前提 |
| L-4 ML 線画抽出 | 学習済みモデルでイラストから線画を推定 | 区分 C | モデルとライセンスは未選定（11章） |

ユーザー調整パラメータ: 黒レベル、白レベル、線色（黒/元の色/任意色）、ノイズ除去強度。

### 5.3 領域分割

1. **二値マスク**: 線画アルファが閾値 `t`（初期値 0.5、調整可）以上を「線」とする
2. **隙間閉じ**: 線の途切れによって隣接領域がつながるのを防ぐ。候補手法:
   - モルフォロジー膨張（単純だが細部が潰れる）
   - 端点検出＋近傍端点同士の線分接続（線の途切れに特化）
   - Trapped-ball 方式（半径 r のボールが通れない隙間を閉じたものとみなす。Zhang et al., 2009 の手法として知られる）
   → MVP は「膨張 + 端点接続」で実装し、Trapped-ball は比較評価の上で採用判断する
3. **ラベリング**: 線以外の画素について連結成分ラベリング（4近傍）を行う。最外周に接する領域は「背景」として扱う
4. **（区分 B）色クラスタリング**: 元画像の線以外の画素を CIELAB 空間で k-means（k は自動推定 or ユーザー指定）。閉領域ラベルと色クラスタの両方を使い、「同一閉領域内で色が明確に異なれば分割」「異なる閉領域でも同色なら同一パーツにまとめるオプション」を提供

### 5.4 パーツ統合・ノイズ除去

- 面積が `min_area`（初期値: 画像総画素数の 0.01%、調整可）未満の領域は、境界を最も多く共有する隣接パーツに吸収する
- パーツ数の上限（初期値 64）を超える場合は面積の小さい順に吸収する。上限は端末メモリから算出（9章）

### 5.5 線下補完

- 線画の下に隠れていた画素を、**最も近いパーツ**（距離変換によるボロノイ割当）で埋める
- 目的: パーツの色を変えても線の下に白い隙間・元の色の縁が残らないようにする（デジタル塗りでいう「線の下まで塗る」状態を自動で作る）
- パーツレイヤーは線画レイヤーの下に配置されるため、補完部分は表示上は線に隠れる

### 5.6 レイヤー生成

- 生成順（上から）: `線画` → `パーツ 1..N`（面積の大きい順）→ `背景`
- 各パーツレイヤーの初期色:
  - 区分 A: 白、またはユーザー選択の「自動配色」（隣接パーツで色相が離れるよう割当）
  - 区分 B: 元画像のクラスタ代表色
- 各パーツは「1色ベタのレイヤー」として生成するか、「元画像の画素をそのまま切り出したレイヤー」として生成するかを選択可能（区分 B/C では後者が見た目を保持できる）
- 自動分解の結果はまとめて1つのレイヤーフォルダ「自動分解」に入れる

### 5.7 処理性能目標

| 画像サイズ | 目標処理時間（中位スマホ相当, 区分 A） |
|---|---|
| 2048 × 2048 | 3 秒以内 |
| 4096 × 4096 | 10 秒以内 |

- 重い処理は Web Worker 上で実行し、UI をブロックしない。進捗表示とキャンセルを必須とする
- パラメータ調整プレビューは縮小画像（長辺 1024px）で行い、確定時にフル解像度で再計算する

> 注: 上記目標値は実測前の暫定値。PoC（12章 Phase 0）で計測し確定する。

## 6. レイヤー編集機能

### 6.1 レイヤー操作（MVP）

| 機能 | 内容 |
|---|---|
| 追加 / 削除 / 複製 | 通常レイヤーの作成、削除、複製 |
| 並べ替え | ドラッグで順序変更 |
| フォルダ | レイヤーのグループ化、フォルダ単位の表示/非表示・不透明度 |
| 表示 / 非表示 | 目アイコン |
| 不透明度 | 0–100% |
| 合成モード | 通常、乗算、スクリーン、オーバーレイ、加算（発光）、比較(暗)、比較(明)、覆い焼きカラー、焼き込みカラー、ハードライト、ソフトライト、差の絶対値、除外、色相、彩度、カラー、輝度 |
| クリッピング | 直下のレイヤー（またはクリッピング基底レイヤー）の不透明部分にのみ表示 |
| 透明度保護 | 既存の不透明画素にのみ描画 |
| 参照レイヤー指定 | 塗りつぶし・自動選択の判定元に指定（自動分解直後は線画レイヤーが参照に設定される） |
| 結合 | 下のレイヤーと結合、表示レイヤーを結合 |
| リネーム | レイヤー名変更 |
| ロック | 編集不可にする |

### 6.2 パーツ専用操作（本アプリ固有）

| 機能 | 内容 |
|---|---|
| パーツ色変更 | ベタ塗りパーツの色をカラーピッカーで一括変更 |
| 色相・彩度・明度調整 | レイヤー単位の HSV/HSL 補正 |
| パーツ分割 | パーツ上に線を引いて2つのレイヤーに分割 |
| パーツ結合 | 複数パーツを1レイヤーに統合 |
| パーツ移動ブラシ | なぞった画素を指定パーツへ移す（境界補正用） |
| パーツ選択 | キャンバス上のタップで該当パーツのレイヤーを選択 |
| 再分解 | パラメータを変えて自動分解をやり直す（既存の手動編集は保持しない旨を警告） |

### 6.3 描画ツール（MVP）

| ツール | 内容 |
|---|---|
| ブラシ | 筆圧対応（Pointer Events の `pressure`）、サイズ・不透明度・硬さ。手ブレ補正（移動平均）|
| 消しゴム | ブラシと同じパラメータ |
| 塗りつぶし | 参照レイヤー対応、許容誤差、隙間閉じ、塗り拡張（px） |
| 選択 | 矩形・投げ縄・自動選択（参照レイヤー対応） |
| 変形 | 選択範囲の移動・拡大縮小・回転 |
| スポイト | 表示色 / 現在レイヤーの色 |
| 取り消し / やり直し | 最低 50 ステップ（メモリ上限に応じて可変） |

### 6.4 MVP 対象外（将来）

- フィルタ類（ぼかし、グラデーションマップ等）
- テキスト、定規、パース定規
- ブラシのカスタム作成
- 動画（タイムラプス）記録

## 7. 画面構成

```
┌──────────────────────────────────────────┐
│ ヘッダー: 戻る / 取り消し / やり直し / 書き出し │
├──────────────────────────────────────────┤
│                                          │
│              キャンバス                   │
│   （ピンチでズーム・回転、2本指タップで取消）  │

├──────────────────────────────────────────┤
│ ツールバー: ブラシ/消しゴム/塗り/選択/… 色 │
```

| 画面 | 主な要素 |
|---|---|
| ホーム（作品一覧） | 新規作成、画像から作成、作品サムネイル一覧 |

| 編集 | キャンバス、ツールバー、レイヤーパネル |
| 書き出し | 形式選択（PNG / PSD / 独自形式）、サイズ、背景透過の有無 |

レスポンシブ: スマホ縦（〜600px）、タブレット、PC の3レイアウト。

## 8. データモデル

```ts
type Document = {
  id: string;
  name: string;
  width: number;            // px
  height: number;           // px
  dpi: number;              // 既定 350
  root: LayerGroup;
  createdAt: string;        // ISO 8601
  updatedAt: string;
  source?: SourceImageInfo; // 自動分解の元画像情報（再分解用）
};

type LayerNode = Layer | LayerGroup;

type LayerBase = {
  id: string;
  name: string;
  visible: boolean;
  opacity: number;          // 0..1
  blendMode: BlendMode;
  clipping: boolean;        // true: 下のレイヤーにクリッピング
  locked: boolean;
};

type Layer = LayerBase & {
  kind: "raster";
  role: "normal" | "lineart" | "part" | "background";
  alphaLocked: boolean;
  isReference: boolean;
  bitmapId: string;         // ピクセルデータへの参照（IndexedDB/OPFS 上）
  bounds: { x: number; y: number; w: number; h: number }; // 非透明領域の外接矩形
  part?: { fillColor?: string; sourceLabel?: number };      // role=part の付加情報
};

type LayerGroup = LayerBase & {
  kind: "group";
  expanded: boolean;
  children: LayerNode[];    // 先頭が最前面
};

type SourceImageInfo = {
  bitmapId: string;
  category: "A" | "B" | "C";
  params: DecomposeParams;  // 再分解時の初期値
};
```

- ピクセルデータはレイヤーの外接矩形（`bounds`）分のみ保持し、全面サイズを確保しない（パーツレイヤーは画像の一部しか占めないことが多いため、メモリ削減効果が大きい）
- 独自保存形式（`.ldraw`）: ZIP コンテナに `document.json` と各レイヤーの PNG を格納（OpenRaster `.ora` と同様の構造。`.ora` での入出力も Phase 2 で検討）

## 9. 非機能要件

| 項目 | 要件 |
|---|---|
| 対応環境 | 最新2バージョンの Chrome / Edge / Safari（iPadOS・iOS 含む）/ Firefox |
| 最大キャンバス | 4096 × 4096 px（端末メモリにより制限。超える入力は縮小を提案） |
| メモリ | RGBA 8bit で 1 レイヤー全面 = 幅×高さ×4 バイト（4096² で 64 MiB）。パーツは外接矩形保持でこれを削減する。iOS Safari には Canvas の合計メモリ上限があるため、実機で上限を計測しレイヤー数上限を決める |
| 描画レイテンシ | ペン入力から画面反映まで 1 フレーム（60fps 端末で約 16ms）以内を目標 |
| オフライン | 全機能がオフラインで動作（PWA）。画像を外部サーバーへ送信しない（ML も端末内で実行） |
| 自動保存 | 編集操作後、一定間隔（例: 30 秒）で IndexedDB/OPFS へ保存 |
| プライバシー | 画像は端末内のみで処理。解析・送信は行わない（ML をサーバー実行に変える場合は明示同意を取る） |
| アクセシビリティ | 主要ボタンにラベル、タッチターゲット 44px 以上 |

## 10. 技術構成案

| レイヤー | 採用候補 | 選定理由 |
|---|---|---|
| アプリ形態 | **Web アプリ（PWA）** | スマホ・タブレット・PC を単一コードで対応。インストール不要で試用障壁が低い。将来ネイティブが必要になれば Capacitor 等で包む |
| 言語 / UI | TypeScript + React（または Svelte） | 型安全、エコシステム |
| 描画・合成 | WebGL2（合成モード・クリッピングをシェーダで実装） | Canvas 2D の `globalCompositeOperation` は主要な合成モードを持つが、クリッピング＋合成モードの組合せやフォルダ単位合成、大量レイヤー時の性能でシェーダ実装の方が制御しやすい。WebGPU は対応状況を見て Phase 2 以降で検討 |
| 画像処理 | Web Worker + WebAssembly（OpenCV.js、または Rust 製の自前処理を wasm 化） | 連結成分ラベリング、距離変換、モルフォロジー、k-means を高速に実行 |
| ML 推論（Phase 2） | ONNX Runtime Web（WebGPU / WASM バックエンド） | 端末内推論。モデルは軽量なものに限定 |
| 保存 | IndexedDB / OPFS（Origin Private File System） | 大容量バイナリの保存 |
| PSD 入出力 | `ag-psd`（JavaScript の PSD 読み書きライブラリ） | ライセンス・対応範囲（合成モード、クリッピング、フォルダ）を採用前に確認 |
| テスト | Vitest（単体）、Playwright（E2E）、分解品質は画像データセットによる回帰テスト | |

### 10.1 フレームワーク構成（v0.2 時点で実装済み）

Vite + React + TypeScript。ディレクトリと責務:

| ディレクトリ | 責務 | DOM 依存 |
|---|---|---|
| `src/core/` | データモデル（8章）、ドキュメント操作（イミュータブル）、取り消し履歴、ビットマップ置き場 | `bitmapStore` のみ |
| `src/io/` | 入力形式判定、PNG/JPEG/SVG のデコード、SVG サイズ解決 | `importImage` のみ |
| `src/decompose/` | 自動分解パイプライン（5章）。Web Worker で実行 | なし |
| `src/render/` | レイヤーツリーの合成（`Compositor` インターフェース） | あり |
| `src/store/` | エディタ状態（React Context + useReducer）、分解結果からのドキュメント生成 | あり |
| `src/ui/` | 画面部品（キャンバス、レイヤーパネル） | あり |

設計上の決定:

- **ドキュメントはイミュータブル、ピクセルは ID 参照**: 取り消し履歴はドキュメントのスナップショットで実装し、ピクセルデータは `BitmapStore` に ID で保持する。これによりスナップショットのコストがツリー構造分だけになる。ピクセル編集時は新しい ID を発行する（コピーオンライト）
- **連続操作の履歴**: スライダー操作中は履歴に積まず、操作終了時に 1 ステップとして確定する
- **合成は差し替え可能**: 現在は Canvas 2D 実装（`Canvas2DCompositor`）。`Compositor` インターフェースを保ったまま WebGL2 実装に置き換える
- **自動分解は DOM 非依存**: Worker・単体テストの両方から同じコードを実行できる。キャンセルは Worker の終了と再生成で行う

## 13. 受け入れ基準（MVP）

1. 白背景・黒線の線画 PNG（2048×2048）を読み込み、自動分解の結果として「線画」レイヤー1枚と、閉領域ごとのパーツレイヤーが生成される
2. 線画レイヤーは線以外が完全透明（アルファ 0）であり、線のアンチエイリアスが保持されている（二値化されていない）
3. 線の途切れ幅が既定パラメータ以下（例: 3px 以下）の場合、途切れの両側が別パーツとして分割される
4. 任意のパーツの色を変更したとき、線と塗りの間に元の背景色（白）の隙間が見えない（線下補完の検証）
5. 自動分解の処理中に UI が操作不能にならず、キャンセルできる
6. 6.1 の全レイヤー操作が動作し、取り消し/やり直しが 50 ステップ以上可能
7. 保存→再読込で、レイヤー構造・合成モード・クリッピング・不透明度が完全に復元される
8. 機内モード（オフライン）で 1〜7 がすべて動作する

## 14. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 線の途切れ・ノイズにより分割品質が安定しない | 体験の中核が損なわれる | プレビューでのパラメータ調整と手動補正ツール（6.2）を MVP に含める。テスト画像セットで回帰評価 |
| モバイルブラウザのメモリ制限 | 大きな画像・多数レイヤーでクラッシュ | 外接矩形保持、パーツ数上限、入力サイズ上限、実機での上限計測 |
| ML モデルのライセンス・学習データ問題 | 商用利用不可、公開後の差し替え | 採用前にライセンス・学習データの出自を確認し記録。区分 A/B は ML 不要で成立させる |
| 既存アプリとの類似 | 権利上の問題 | UI・名称・アイコンは独自設計。機能水準の参考に留める |
| ユーザーが他者の画像を分解・改変 | 著作権侵害の助長 | 利用規約で自作または権利を有する画像に限定する旨を明記 |
